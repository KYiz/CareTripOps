# CareTrip Ops V4.0 — Full Business, Agent Value, and Reliability Audit

**Audit date:** 9 October 2026 (Pacific/Auckland)  
**Scope:** Current source and locally executable checks. No Git command, Docker lifecycle operation, real Gemini call, or change to business logic was made in this audit. "Implemented" means code exists; it does not imply runtime acceptance.

## Executive assessment

CareTrip has a real, bounded business workflow for **one synthetic Auckland package scenario**. The LangGraph state machine connects requirements, a locally generated illustrative itinerary, fixed supplier fixtures, deterministic evidence arbitration, a persisted human decision, and one simulated order with an idempotency key. This is more than a static chatbot. Its current independent value is a reviewable execution boundary and an audit trail, not a superior general travel answer.

It is **not yet a reliably demonstrated end-to-end service** in this revision. A fresh database migration has a source-proven duplicate-column defect; current database, browser, voice, and concurrency acceptance could not be run here. Queenstown, Rotorua, Taupō, Wellington, and Christchurch can produce destination-specific illustrative outlines from local catalogs, but have no supplier offers or booking path. No real supplier or payment transaction exists.

Terminology in this report: **Illustrative Itinerary** is an unverified daily idea; **Preliminary Offer** is a synthetic quote before final evidence; **Verified Offer** is a synthetic quote with a PASS assessment; **Mock Booking** is a committed simulated order; **Real Supplier Booking** is absent.

### Flow and data consistency

`build_graph()` defines actual conditional routes for missing requirements, no candidate, evidence verdict, and human decision. PostgreSQL checkpoint thread IDs use the Case ID; revision threads use `guide:{case_id}:{proposal_id}`. Approval/order business rows are separate from checkpoints, so a DB commit and checkpoint save cannot be claimed atomic. `Dashboard`, `PhoneSimulator`, and `GuidePanel` call the same `/api/cases/{id}` family through `frontend/src/api/client.ts`; the two main views poll a shared snapshot. `My Trips` is browser-local Case IDs, not an account-wide trip history. Accepted Guide revisions update illustrative days only, leaving offers and orders unchanged; that separation prevents direct price mutation but can leave an approved package visually paired with a newer unverified daily outline.

## B. Agent Value Assessment

**Real value in code:** explicit state transitions; evidence-gated offer selection; persisted approval before execution; skill-level checks on the only side-effecting booking operation; deterministic idempotency; Case-specific audit events; bounded recovery entry points. These make the fixed mock scenario more controllable than an unconstrained chat response.

**Replaceable by general AI or ordinary application code:** natural-language requirement extraction, generic itinerary prose, local recommendation templates, deterministic text-guide responses, and the hard-coded supplier catalog. Worker count alone is not evidence of autonomy. The Manager's concrete value is routing a blocked candidate to a rerank; most other nodes orchestrate deterministic functions. Planner and Reviewer are two calls to the same configured Gemini model, with one optional revision; their practical quality gain has not been evaluated.

**Future execution value:** supplier adapters, trusted evidence, availability and quote refresh, authorized real reservations, supplier acknowledgements, cancellation/refund handling, and live trip events. The current Skills are a useful seam but `search_suppliers()` and `verify_evidence()` directly depend on fixed product IDs, so swapping in real APIs needs an adapter contract and error semantics, not just a URL change.

## E. Final assessment

The code forms a **conditional simulated closure** for Auckland, not a verified current deployment. The Agent workflow has practical control and audit value in that scenario; planning prose and the five other destinations remain largely illustrative. Gemini requirements extraction, two-role itinerary calls, and Live voice are implemented as selectable paths, but were not run in this audit. HITL and order idempotency have coherent code and database constraints, while migration and current integration evidence block a reliability claim. Cross-Case tokens reduce the former ID-only access risk for new Cases, but multi-user concurrency and browser continuity are unverified. The Web, Mobile, and Dashboard components share an API client and Case ID; runtime synchronization was not observed here.

For a stable Hackathon MVP, first make the fresh/existing database migrations pass, then prove the Auckland approve/reject/retry/recovery paths with current PostgreSQL tests and a browser smoke test, then validate one representative non-Auckland itinerary and the Guide's truthful labeling. If only three fixes are allowed: **(1) repair the migration chain, (2) run and fix the current security/booking/recovery end-to-end tests, (3) prevent an accepted illustrative revision from appearing to alter an approved package.** Commercial B2C/B2B2C expansion is architecturally possible around the workflow and Skills, but requires real identity/permission, supplier contracts and adapters, quote/inventory verification, actual booking lifecycle, reconciliation, and privacy controls.
